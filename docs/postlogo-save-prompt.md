# Следующий ожидаемый экран: запрос создания сохранения

По наблюдению пользователя в эмуляторе после SQUARE ENIX должен появиться
внутриигровой запрос создания сохранения; подтверждение — два отдельных
нажатия A. Это ближайший критерий проверки, до титульного меню.

## Трассировка после исправления APT

`/tmp/dq8-save-probe-long.err` — 45-секундный запуск диагностического runner.
Raster выключен только в этом отдельном `/tmp` runner, поэтому этот лог
подтверждает ход CPU и ожидания, а не изображение на экране. Основной runner
`/tmp/dq8-apt-v3` с настоящим raster не менялся.

Уточнён адрес объекта, который опрашивает главный поток:

- `0x0024F798` вызывает инициализацию `0x002FBD40`.
- Объект — **0x087F5948**, передаётся в r9 основного потока. Адрес
  `0x087F5850` из раннего snapshot — r7, это другой объект.
- State по object+0xC (`0x087F5954`) остаётся 0; главный цикл ждёт 1 либо 7.
- Создан worker 11 (`0x0005000B`), descriptor `0x087F7E88`, entry
  `0x002FA2EC`, аргумент `0x087F5948`. Descriptor корректен: callback
  действительно исполнен; прежний сбой callback=0x248 здесь не наблюдается.
- Worker выполняет `0x002FBBE0 -> 0x002FAE68`, затем снова ожидает LightEvent
  по object+0x20 (`0x087F5968`). Это не ожидание кнопки A.
- `0x002FAE68` вызывает `0x004CA0E4` через handle из object+0x18 и получает
  нулевой count в выходном слове. Эта ветка выходит без смены state.
- LightEvent после первого прохода не получает следующего сигнала;
  остальные краткоживущие worker 7–10 уже завершены.

Следующий предмет расследования: кто должен заполнить count/сигнализировать
данный объект и почему callback/производитель данных не завершает этот шаг.
Не следует принудительно записывать state=1/7, сигнализировать event каждый
кадр или подменять запрос сохранения картинкой: это скроет причину.
